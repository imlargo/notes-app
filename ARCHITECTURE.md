# Architecture

The app is layered so the logic and the persistence don't depend on React. domain/ is the model and the geometry, pure functions I can test without mounting anything. services/ hides persistence behind an async NoteRepository with two implementations, both with fake latency on purpose so the UI is written against real async I/O, and a REST backend would be one more class. hooks/ is split by what each part needs to know rather than by size: useNotes owns the data, useBoardGestures owns the pointers and knows nothing about persistence, and useBoardBounds sits outside both because gestures and keyboard commands both clamp against the board.

Every write is optimistic, and making them consistent was the point. Moving was already optimistic while creating and deleting waited for the round trip, so the app taught you two different things about whether your action had landed. Now the screen updates first and the repository after, and a failure puts the previous value back. Text is the exception on purpose, reverting what someone typed because a save failed is worse than a stale disk. Writes also carry only the changed fields and the response is thrown away: drop a note, type while the write is in flight, and the echo would put your old text back.

The main decision on the interaction side was to drag with one set of pointer handlers on the board instead of wiring listeners per note. The gesture is a union kept in a ref since it changes every frame and nothing renders from it, and the repository is only written when the gesture ends. The final geometry comes from the gesture rather than from reading state back, so the commit doesn't depend on React having rendered the last pointermove. Notes are read through a ref for the same family of reasons, notes is a new array every frame and closing over it gives every callback a new identity, which re-renders all of them.

Accessibility wasn't an afterthought, it shaped the component API. Every note is focusable and can be moved, resized, edited and deleted without a mouse, with one tab stop each on purpose since thirty notes with two stops is sixty stops to cross a board. Selection is drawn rather than implied, because the colour control means two different things depending on whether a note is selected and focus-visible can't show which, it disappears the moment you click with a mouse. Blur deliberately doesn't clear it either, tabbing to the toolbar would kill it on the way. Successes go to a polite live region and failures to role=alert, never to both.

Every test here runs without React. domain/ and the reducer are pure functions checked directly, including that patching one note leaves the identity of every other one alone, which is what lets the memoised notes skip a render. The two repositories share one contract suite that runs twice, since the point of the interface is that they are interchangeable. That is what keeps catching them disagreeing: one reused the id of a deleted note, both reported success for an update to a note that was not there so the rollback could never fire, one picked a colour for a colourless draft and the other left it undefined, one let a draft carry its own id in and override the one it was supposed to generate, and both would happily move a note onto another note's id. The localStorage one gets a Map behind a Storage interface rather than a whole DOM, so the suite runs in node with vitest as its only dependency.

What that leaves uncovered is the wiring, which is where the rest of the bugs are. Nothing renders a board, so nothing checks that a drag commits the rect it drew, that dropping on the trash deletes rather than moves, or that the whole board can be crossed and emptied from the keyboard. That is the next thing to write.
