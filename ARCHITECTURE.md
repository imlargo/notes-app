## Architecture descripcion

The app is layered so the logic and the persistence don't depend on React. domain/ is the model and the geometry, pure functions I can test without mounting anything. services/ hides persistence behind an async NoteRepository with two implementations, in-memory and localStorage. Both have fake latency on purpose so the UI is written against real async I/O. A REST backend would be one more class and nothing above it changes. state/ is a reducer, hooks/ is where the behaviour lives and components/ only render.

hooks/ is split by what each part needs to know rather than by size. useNotes owns the notes and everything that talks to the repository. useBoardGestures owns the pointers and knows nothing about persistence, it receives what to do as callbacks. useBoardBounds sits outside both because the gestures and the keyboard commands both clamp against the board, and if it lived inside either one the other would have to ask it for the size. useBoard composes the three and keeps what is only about the screen, which note is selected and which one is being edited.

Every write is optimistic and all four follow the same policy, which was the point, the inconsistency was worse than either choice on its own. The screen updates first, the repository after, and the previous value goes back if it fails. Creating a note hands it a temporary negative id so it appears before the write starts and swaps it for the stored one when that lands, in place so the z order survives. Only the changed fields are sent and the response is dropped on purpose, applying it would undo anything typed while the write was in flight and the client already has the value it just wrote.

The main decision on the interaction side was to drag with one set of pointer handlers on the board instead of wiring listeners per note. Hit testing happens on pointerdown and the current gesture is a union kept in a ref since it changes every frame and nothing renders from it. The repository only gets written when the gesture ends, and the final geometry is derived from the gesture rather than read back from state so the commit doesn't depend on the last frame having rendered. Nothing reads the notes array through a closure either, it goes through a ref, otherwise the callbacks get a new identity every frame and the memo on StickyNote stops preventing anything.

Accessibility wasn't an afterthought, it shaped the component API. A drag only interface is invisible to a keyboard so every note is focusable and can be moved, resized, edited and deleted without a mouse. Focus goes somewhere sensible after a note disappears and changes get announced. Selection is drawn instead of implied, a control that means two different things has to show which one it means. Types work the same way, the gesture is a union instead of a pile of flags so the wrong state doesn't compile. That part matters more to me than squeezing in every feature
